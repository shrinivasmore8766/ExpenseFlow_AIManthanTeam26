# Basic Security Checklist

**Target:** the local ExpenseFlow stack only, using seeded synthetic data. No destructive tests were run. Every write attempt on the audit log ran inside a transaction that was rolled back.
**Executed:** 2026-11-27.
**Evidence:**
- [evidence/api-tests.txt](evidence/api-tests.txt): API tests AUTH, RBAC, ISO and SEC
- [evidence/frontend-results.json](evidence/frontend-results.json): browser checks FE-xx
- [evidence/security-db-log-checks.txt](evidence/security-db-log-checks.txt): database, log and source checks
- [evidence/backend-unit-tests.txt](evidence/backend-unit-tests.txt): unit tests

> This is a **basic** checklist for a hackathon build, **not** a penetration test or a security certification. Passing it does not mean the application is secure. Out of scope: TLS, dependency CVE scanning (owned by the CI/CD phase), DoS, session fixation over HTTPS, infrastructure hardening.

**Result: 13 Pass, 2 Fail, 0 Not Tested.**

| # | Security check | How it was tested | Expected behaviour | Actual result | Status | Remediation |
|---|---|---|---|---|---|---|
| 1 | Authentication and invalid login attempts | AUTH-01 to 05, SEC-11 (15 wrong passwords in a row), FE-01 | Bad credentials are refused, with no detail leaked and no browser popup. Repeated failures should be throttled or locked. | No credentials, a wrong password or an unknown user all get **401** with an identical body (no user enumeration) and no `WWW-Authenticate` header. The UI shows "Invalid username or password." **But** 15 failures in a row were all accepted for evaluation, and the correct password worked straight after: no lockout or throttling. | **Fail** | DEF-04: add a failed-login counter or rate limiter (for example per username and IP, with back-off), and audit lockouts. |
| 2 | Password handling and storage | DB query on `employee.password_hash`; `/api/me` response | Salted adaptive hashes. Passwords never returned. | All **150/150** hashes are BCrypt (`$2a$`, 60 characters). `/api/me` has no password fields. Passwords appear in no log line (0 matches in about 4.4k lines). | Pass | Note: HTTP Basic sends the password on every request, so **HTTPS is mandatory** in any real deployment. The UI keeps the Basic header in `sessionStorage` (an accepted demo trade-off, ADR 0004). |
| 3 | Authorization and role-based access | 25 RBAC tests: each role against each restricted endpoint. FE-02 and FE-04 for navigation and route guards. | Role-only endpoints answer 403 to other roles. The UI hides and guards pages. | 16 forbidden combinations → **403** with a generic message. 9 allowed combinations → 200. The UI shows "You do not have access to this page" for an employee on `/approvals` and `/payouts`, and for a manager on `/payouts`. | Pass | — |
| 4 | Employee-to-employee data isolation | ISO-01 to 05, FE-06 | An employee sees only their own claims. Other claims return 404, so their existence isn't revealed. | The `/api/claims` list holds only the caller's claims. Another employee gets **404** on view, rename, add line, submit, delete and receipt download. A manager from another department gets 404 on view and approve. The UI shows "Claim not found". | Pass | — |
| 5 | Unauthorized API access | AUTH-01, RBAC, `GET /actuator/*` | Every `/api/**` call needs authentication. | All `/api/**` calls without credentials get 401. `/actuator/health` is public (intended). **Observation:** `/actuator/prometheus` is also public (a documented demo decision). | Pass | Restrict `/actuator/prometheus` to the internal network or require authentication outside the demo. |
| 6 | Privilege escalation attempts | SEC-04 (mass assignment), THR-04, DEL-05, the `ApprovalRulesTest` permission set | Clients can't set status, owner or amounts. Nobody approves their own claim, skips a level or exceeds delegated rights. | `status`, `employeeId`, `approvedAmount` and `sampleAudit` in the request body are **ignored** (the claim stays DRAFT and owned by the caller). Self-approval → 403. Skipping a level → 403. A manager's delegate on an auditor-level claim is denied. The claimant's own delegation grant is ignored. | Pass | — |
| 7 | Receipt upload file type and size validation | SEC-08, SEC-09, SEC-10, `ReceiptValidationTest`, UI dropzone | Only PDF, JPEG and PNG, detected from the content. Maximum 5 MB. | HTML/script content named `receipt.png` → **400** "Only PDF, JPEG or PNG receipts are allowed." A file over 5 MB → **413**. PNG bytes named `.pdf` are stored as `image/png`: the type comes from the content, not the client. The UI checks type and size before uploading. | Pass | — |
| 8 | File upload access restrictions | ISO-03, SEC-10, FE-14, `ReceiptValidationTest` | Receipts are reachable only through the authorised endpoint, with no path tricks. | Another employee gets 404. Files are stored under random UUID names, and the client's file name is never used. `../../etc/passwd`-style names are rejected. Downloads send `X-Content-Type-Options: nosniff`. The UI loads receipts through an authenticated blob URL. | Pass | — |
| 9 | SQL injection input checks | SEC-01, SEC-02 (4 payloads), code review of the repositories | User input never changes queries. | The title `x'); DROP TABLE claim;--` is stored as plain text and the tables are intact. Malformed or injected query parameters (`minAmount=1 OR 1=1`, `status=x'--`, `departmentId=1;DROP`) get **400**, with no SQL or exception text in the body. All queries are Spring Data or JPQL with bound parameters. | Pass | — |
| 10 | Cross-site scripting input checks | SEC-03 (API), FE-08 (browser) | Script in user input is shown as text and never runs. | `<img src=x onerror=…><script>…</script>` in a claim title is shown as plain text on My claims. No `<img src="x">` element was created, and the `window.__xss` flag was never set. React escapes all output, and `dangerouslySetInnerHTML` is used nowhere. | Pass | Add a `Content-Security-Policy` header in the nginx or production setup as defence in depth. |
| 11 | CSRF protection where applicable | Review of `SecurityConfig`; SEC-07; AUTH-05 | State-changing requests can't be forged from another site. | Authentication is a per-request `Authorization` header, **not cookies**: no `Set-Cookie` is ever issued, so a forged cross-site request carries no credentials. CSRF tokens are therefore not needed (CSRF is disabled on purpose). A foreign `Origin` gets no CORS grant. | Pass | If you move to cookie sessions or JWT in cookies, turn CSRF protection back on. |
| 12 | Sensitive information in logs and API responses | Scan of all backend logs (about 4.4k lines). SEC-02 and SEC-05 error bodies. Request log. | No credentials or stack traces sent to clients, and no secrets in logs. | 0 log lines contain passwords, Basic tokens or hashes. Malformed JSON and bad parameters return a generic ProblemDetail with no class names or stack traces. **0 HTTP 500** responses in about 3,400 requests. Logs contain user and claim ids only. The CSV export holds bank details by design, and only the Finance Head can download it. | Pass | DEF-05 (Hibernate ERROR noise) is not sensitive, but should be handled in alerting. |
| 13 | Secrets and credentials in source and configuration | `git ls-files` and `git grep` scan ([evidence](evidence/security-db-log-checks.txt), items 10–11) | No real secrets committed. No usable default credentials. | No `.env`, key or credential files are tracked (`.env` is git-ignored). **But** working fallback defaults are committed: `application.yml` has a DB password default of `expenseflow` and `APP_DEMO_PASSWORD` defaulting to `Demo@123`, `.env.example` has `Demo@123`, and `LoginPage.jsx` hard-codes the demo password for the quick-login buttons. All 150 seeded accounts share it. These are demo credentials and documented, but they would be dangerous if this configuration were deployed. | **Fail** (low risk for the demo) | Remove the fallback defaults outside a `demo` profile, make startup fail without `DB_PASSWORD`, turn seeding off by default, and show the quick-login buttons only in demo builds. |
| 14 | Audit trail integrity | DB: `UPDATE` and `DELETE` on `audit_log` inside rolled-back transactions. AUD-01. History assertions in APR-03, THR-04, DEL-04 and E2E-09/10. | Every action is recorded, and records can't be changed. | The trigger blocks both: "audit_log is append-only: UPDATE is not allowed" and "…DELETE is not allowed". Every action type exercised today appears in `audit_log` (20 action types). Claim history keeps the actor, on-behalf-of, the transition, the comment and the time, in order. | Pass | The table owner could still drop the trigger. A hash chain or external log shipping would make tampering detectable (noted as NICE in the architecture doc). |
| 15 | Unauthorized payout or approval attempts | RBAC (payout endpoints for employee, manager and auditor), PAY-04, PAY-05, THR-04, APR-02 | Only the Finance Head runs payouts. Approvals follow the chain. Paid and rejected claims are final. | Employee, manager and auditor calls to payout create, list, CSV or mark-paid → **403**. Marking a batch paid twice → **409**. A rejected claim can't be approved (409) and never appears in the eligible list. DB: 0 rejected claims with a payout, and 0 paid claims without a batch. | Pass | — |
